# Blueprint: vLLM Semantic Router + AI Gateway (Helm only)

[semantic-router](https://github.com/vllm-project/semantic-router) routes
incoming LLM requests to different backend models based on the content of the
request. This blueprint installs the router, its dashboard, an Envoy AI Gateway
data plane that puts the router in the request path as an external processor,
mandatory per-client API key authentication, and per-API-key token quota — on
**any** Kubernetes cluster, with plain Helm and `kubectl`.

There is a sibling blueprint, [`../semantic-router`](../semantic-router), that
does the same thing on a cluster-forge cluster: delivered through ArgoCD from a
Gitea overlay repo, published on the cluster's shared `https` Gateway with TLS,
and using cluster-forge's own installed Envoy Gateway and AI Gateway. Use that
one on a bloomed cluster. Use this one anywhere else, or when you want the whole
stack installed and owned by Helm releases you control.

That sibling's README goes deeper on routing decisions, model cards, dashboard
accounts, and quota tiering. None of that is repeated here — this README covers
only what differs.

## What it installs

| Release / object | Namespace | What it is |
|---|---|---|
| `envoy-gateway` | `envoy-gateway-system` | Envoy Gateway control plane, configured to call AI Gateway as an extension |
| `GatewayClass/envoy-gateway` | cluster-scoped | what `sr-gateway` binds to |
| `envoy-ai-gateway-crds` | `envoy-ai-gateway-system` | `AIGatewayRoute`, `AIServiceBackend`, `QuotaPolicy`, … |
| `envoy-ai-gateway` | `envoy-ai-gateway-system` | the AI Gateway controller + extproc image |
| `envoy-ai-gateway-ratelimit` | `envoy-gateway-system` | `envoyproxy/ratelimit` + a Redis, which is what QuotaPolicy actually counts against |
| `semantic-router` | `semantic-router` | the router and its dashboard |
| `Gateway/sr-gateway` + policies | `semantic-router` | a dedicated Envoy data plane with the router wired in as ext_proc |
| `Service/sr-gateway` | `envoy-gateway-system` | stable ClusterIP in front of that data plane |
| `Secret/semantic-router-client-keys` | `semantic-router` | client API keys, generated by the installer |

## Prerequisites

- A kubeconfig pointing at a cluster, with cluster-admin.
- `helm` 3, `kubectl`, `git`, `openssl`.
- A default StorageClass, or a real class name set in
  `values/semantic-router.yaml` (the router needs a PVC for its model cache).
- A reachable vLLM backend serving the model you want to route to. The router
  installs fine without one, it just has nothing to route to.

Explicitly **not** required: cert-manager, a LoadBalancer, ArgoCD, Gitea,
cluster-forge, or the Gateway API Inference Extension CRDs.

The AI Gateway chart's mutating-webhook certificate is issued by the chart's own
built-in genCA path rather than cert-manager. That path is unsafe under ArgoCD
(which renders Helm without a live cluster, so its `lookup` guard always misses
and every sync mints a fresh CA), but it is stable under `helm upgrade`, which
renders against the live cluster. Set
`controller.mutatingWebhook.certManager.enable=true` if you have cert-manager
and would rather it own the cert.

## Build the patched AI Gateway image

**Read this before relying on per-tenant token quota.** On the upstream AI
Gateway images this blueprint defaults to, `manifests/quota.yaml` installs
cleanly, reports counters, and enforces nothing useful: the counter each
tenant's bucket checks increments by **1 per request**, while the real token
cost is charged to a different, shared-across-all-keys counter that fires after
the stream has already ended and can never deny. So `limit` behaves as requests
per window rather than tokens, and one tenant's spend is indistinguishable from
another's.

The fix is [theagentrouter/agent-router#2664](https://github.com/theagentrouter/agent-router/pull/2664)
("fix: charge per-tenant token cost for Distinct bucket rules"), which is open
and unreleased. It is a controller-side change only — the request-time builder
emits a `RequestHeaders` rate-limit action keyed on the caller's header while
the stream-done builder emits a `GenericKey` action with a constant descriptor
value, so for a `Distinct` bucket rule the two phases never resolve to the same
bucket. Full write-up in this repo's
`envoy-ai-gateway-quotapolicy-cost-metadata-mismatch-2026-09-08.md`.

Until it ships, build the controller yourself:

```bash
git clone https://github.com/theagentrouter/agent-router.git
cd agent-router
git fetch origin pull/2664/head:pr-2664
git checkout pr-2664
```

**Push to a registry** (the normal case — any cluster with more than one node
needs this):

```bash
make docker-build.controller ENABLE_MULTI_PLATFORMS=true \
    DOCKER_BUILD_ARGS="--push" OCI_REGISTRY=docker.io/myorg TAG=pr2664
make docker-build.extproc    ENABLE_MULTI_PLATFORMS=true \
    DOCKER_BUILD_ARGS="--push" OCI_REGISTRY=docker.io/myorg TAG=pr2664
```

**Or build locally and load into the cluster** (single-node kind / k3s / minikube):

```bash
make docker-build.controller DOCKER_BUILD_ARGS="--load" OCI_REGISTRY=localhost TAG=pr2664
make docker-build.extproc    DOCKER_BUILD_ARGS="--load" OCI_REGISTRY=localhost TAG=pr2664

# kind
kind load docker-image localhost/ai-gateway-controller:pr2664
kind load docker-image localhost/ai-gateway-extproc:pr2664

# k3s / containerd
docker save localhost/ai-gateway-controller:pr2664 | sudo ctr -n k8s.io images import -
docker save localhost/ai-gateway-extproc:pr2664    | sudo ctr -n k8s.io images import -

# minikube
minikube image load localhost/ai-gateway-controller:pr2664
minikube image load localhost/ai-gateway-extproc:pr2664
```

The Makefile derives `OCI_REPOSITORY_PREFIX = ${OCI_REGISTRY}/ai-gateway`, so
the images land at `<registry>/ai-gateway-controller:<tag>` and
`<registry>/ai-gateway-extproc:<tag>`. The chart's `imagePullPolicy` default is
already `IfNotPresent`, so a locally loaded image is used without further
configuration.

Then point the install at them:

```bash
export AIGW_CONTROLLER_IMAGE=docker.io/myorg/ai-gateway-controller:pr2664
export AIGW_EXTPROC_IMAGE=docker.io/myorg/ai-gateway-extproc:pr2664
```

PR 2664 does not change extproc, but build both from the same tree anyway so the
two images cannot skew.

One caveat: the PR is based on `main`, which is past the chart version vendored
in this repo (v1.0.0), and the `QuotaPolicy` schema has moved between the two. If
you hit a CRD validation error or a field the controller ignores, point the
charts at the same checkout you built from:

```bash
export AIGW_CRDS_CHART=/path/to/agent-router/manifests/charts/ai-gateway-crds-helm
export AIGW_CHART=/path/to/agent-router/manifests/charts/ai-gateway-helm
```

**Once the fix is in an upstream release, delete this whole step**: drop the
environment variables and bump the tags in `values/envoy-ai-gateway.yaml`.

## Configure before installing

Three files have `TODO-` placeholders. `install.sh` refuses to run while any
remain:

```bash
grep -rn 'TODO-' values/ manifests/
```

| File | What to fill in |
|---|---|
| `values/semantic-router.yaml` | model name, the ID your backend expects, your vLLM endpoint, and the routing decision — also has a second, `TODO-your-complex-model` entry (see "Complexity routing" below) |
| `manifests/gateway-routing.yaml` | the `x-selected-model` rule, the `AIServiceBackend`/`Backend` pair, and your vLLM Service FQDN for both models above — the `Backend`'s `port` must equal the real Service port, or every request 503s with `connection termination` and nothing in the router's own logs says why |
| `manifests/quota.yaml` | the backend to meter, the model name, and the token budget — or delete the file if you do not want token quotas |

The model name must be **the same string** in every one of those places, or
requests match no route and fall to the catch-all. Read
[`../semantic-router/README.md`](../semantic-router/README.md) for how routing
decisions, model cards and additional backends work — it applies unchanged.

### Complexity routing (optional)

`values/semantic-router.yaml` ships with a second model
(`TODO-your-complex-model`) and a `routing.decisions` set that sends hard/
complex prompts to it and easy/factual prompts to the primary model — see
[`../semantic-router/examples/complexity-routing-example.md`](../semantic-router/examples/complexity-routing-example.md)
for the pattern. Fill in both models' placeholders (a real bigger model, or
the same backend twice if you just want the routing wired without two real
models yet) or delete the second model, its `gateway-routing.yaml` rule/
backend pair, and its `modelCards`/`decisions` entries if you don't want it.

## Install

```bash
./install.sh
```

Everything is `helm upgrade --install`, so re-running it is safe and is the
normal way to apply a config change. Dry run first if you want:

```bash
DRY_RUN=1 ./install.sh
```

The client API key Secret is generated on the cluster on first run and **printed
once**. Re-runs never touch an existing Secret. Add more clients later without
disturbing the existing keys:

```bash
kubectl -n semantic-router patch secret semantic-router-client-keys \
  --type merge -p "{\"stringData\":{\"second-client\":\"$(openssl rand -hex 32)\"}}"
```

The key *name* is what per-key quota buckets on. Never reuse a name for a
different tenant — they inherit the old tenant's accumulated spend.

If you would rather not run the script, it is a thin wrapper over these:

```bash
helm upgrade --install envoy-gateway ../../../sources/envoy-gateway/v1.8.1 \
    -n envoy-gateway-system --create-namespace -f values/envoy-gateway.yaml
kubectl apply -f gatewayclass.yaml
helm upgrade --install envoy-ai-gateway-crds ../../../sources/envoy-ai-gateway-crds/v1.0.0 \
    -n envoy-ai-gateway-system --create-namespace
helm upgrade --install envoy-ai-gateway ../../../sources/envoy-ai-gateway/v1.0.0 \
    -n envoy-ai-gateway-system -f values/envoy-ai-gateway.yaml \
    --set controller.image.repository=docker.io/myorg/ai-gateway-controller \
    --set controller.image.tag=pr2664 \
    --set extProc.image.repository=docker.io/myorg/ai-gateway-extproc \
    --set extProc.image.tag=pr2664
helm upgrade --install envoy-ai-gateway-ratelimit ../../../sources/envoy-ai-gateway-ratelimit/0.1.0 \
    -n envoy-gateway-system
kubectl create namespace semantic-router --dry-run=client -o yaml | kubectl apply -f -
helm upgrade --install semantic-router <chart> -n semantic-router -f values/semantic-router.yaml
# then manifests/, IN THIS ORDER -- see below
kubectl apply -f manifests/sr-gateway-config.yaml
kubectl apply -f manifests/sr-gateway-proxy-config.yaml
kubectl apply -f manifests/sr-gateway.yaml
kubectl apply -f manifests/sr-gateway-service.yaml
kubectl apply -f manifests/sr-gateway-extproc.yaml
kubectl apply -f manifests/gateway-routing.yaml
kubectl apply -f manifests/quota.yaml
```

The manifest order is not cosmetic. If the AI Gateway controller reconciles the
`AIGatewayRoute` before its parent `Gateway` exists, it logs `Gateway not found`
and leaves that Gateway's pushed route configuration with **zero virtual hosts,
permanently, with no retry** — every request then 404s with an Envoy `NR`
response flag and nothing in either object's status says why. Recovering needs a
genuine spec-level edit to the `AIGatewayRoute` (an annotation change does not
bump `metadata.generation` and does not trigger a reconcile).

## Reaching it

The `sr-gateway` data plane is a **plain HTTP listener with no TLS**. This
blueprint installs no edge Gateway and terminates no certificate — that is the
main thing it drops relative to the cluster-forge sibling, which fronts the same
data plane with a TLS-terminating shared Gateway.

```bash
kubectl port-forward -n envoy-gateway-system svc/sr-gateway 8080:8080

curl -sS localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $YOUR_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

To expose it directly on a cluster that has a LoadBalancer, edit
`manifests/sr-gateway-proxy-config.yaml`:

```yaml
      envoyService:
        type: LoadBalancer   # or NodePort
```

**Do not put that address on the internet as-is.** API keys travel in a plaintext
`Authorization` header over an unencrypted listener. Anything reachable outside
the cluster needs TLS terminated in front of this — your own Ingress, Gateway, or
service mesh.

## Dashboard

No HTTPRoute is created for it (there is no Gateway to attach one to), so:

```bash
kubectl port-forward -n semantic-router svc/semantic-router-dashboard 8700:8700
```

Upstream's bootstrap endpoint is public and unauthenticated — first stranger
to load the URL claims admin. `dashboard.allowOpenBootstrap` defaults to
`true` here since this blueprint has no HTTPRoute for the dashboard (reachable
only via port-forward, above) — fine for a demo/kind cluster. Sets
`DASHBOARD_ALLOW_OPEN_BOOTSTRAP=true` on the dashboard container; set that env
var directly via `extraEnv` if you're overriding the deployment some other way
than this value. Set `allowOpenBootstrap: false`, or provision an admin via
`extraEnv` instead, before exposing this dashboard any wider than a
port-forward. See the sibling blueprint's "Dashboard access" section for the
account options.

## Verify

1. Pods: `kubectl -n envoy-gateway-system get pods` shows `envoy-gateway`, the
   `sr-gateway` proxy, `envoy-ai-gateway-ratelimit` and its Redis all Running.
2. The image override actually landed:
   ```bash
   kubectl -n envoy-ai-gateway-system get deploy ai-gateway-controller \
     -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'
   ```
3. The extproc sidecar was injected into the `sr-gateway` proxy pod — this is
   what a mutating-webhook certificate problem breaks, and it fails silently:
   ```bash
   kubectl -n envoy-gateway-system get pods \
     -l gateway.envoyproxy.io/owning-gateway-name=sr-gateway \
     -o jsonpath='{.items[*].spec.containers[*].name}{"\n"}'
   ```
4. Auth: the `curl` above returns 200 with a valid key and **401 without the
   header**. A 200 without a key means the `SecurityPolicy` did not attach.
5. Token accounting: the proxy's access log shows non-empty `llm_input_token`,
   `llm_output_token`, `llm_total_token` and `api_key_id`. Always-empty token
   fields mean `llmRequestCosts` is not reaching dynamic metadata, and quota is
   charging nothing regardless of what the policy says.
   ```bash
   kubectl -n envoy-gateway-system logs -l gateway.envoyproxy.io/owning-gateway-name=sr-gateway -c envoy --tail=5
   ```
6. Routing is really configured: `virtual_hosts` is non-empty in the proxy's
   `/config_dump` for route config `semantic-router/sr-gateway/http`. Empty is
   the permanent `Gateway not found` failure described above.
7. **Quota, the reason the custom image exists.** Set `shadowMode: false` and a
   small `limit` in `manifests/quota.yaml`, re-apply, then drive traffic from
   two different API keys and watch the counters:
   ```bash
   kubectl -n envoy-gateway-system exec deploy/envoy-ai-gateway-ratelimit-redis -- \
     redis-cli --scan
   ```
   Correct behaviour: each key has its own counter, incrementing by **real token
   cost** rather than by 1 per request, and the heavy key starts returning 429
   while the light key keeps working. On the upstream image you will instead see
   the per-key counters incrementing by 1 and the token cost pooled into a single
   shared counter — which is the defect, and the contrast is the cleanest way to
   confirm your patched image is actually in use.

   Redis keys are suffixed with a `duration`-aligned epoch bucket
   (`..._<unix-ts>`), so if you drive traffic one `curl` at a time with a slow
   tool round-trip between each (a `kubectl exec` to check Redis takes longer
   than a 1m bucket), every "next" request lands in a fresh, empty bucket and
   looks uncharged even on a working image. Fire requests back-to-back in one
   shell loop and check Redis only after, not between, each one.

8. **Complexity routing**, if you filled in the second model (see above): set
   `model` to `"auto"` and compare an easy vs. hard prompt:
   ```bash
   curl -sS localhost:8080/v1/chat/completions \
     -H "Authorization: Bearer $YOUR_KEY" -H 'Content-Type: application/json' \
     -d '{"model":"auto","messages":[{"role":"user","content":"What is the capital of France?"}]}'
   curl -sS localhost:8080/v1/chat/completions \
     -H "Authorization: Bearer $YOUR_KEY" -H 'Content-Type: application/json' \
     -d '{"model":"auto","messages":[{"role":"user","content":"Explain trade-offs between consistency and availability in distributed systems"}]}'
   ```
   Correct behaviour: the router's logs show a `routing_decision` picking your
   primary model for the first prompt, your complex model for the second
   (`kubectl -n semantic-router logs deploy/semantic-router --tail=20`). If
   both models point at the same backend for now, the response body won't
   tell them apart — the decision log is the check.

## Known defects still live

- **`spec.serviceQuota` is inert.** No Redis key of any shape is created for it.
  Use `perModelQuotas` only. (`envoy-ai-gateway-servicequota-inert-2026-09-09.txt`)
- **`perModelQuotas` isolation does not hold across backends.** Traffic to a
  targeted backend that has no `perModelQuotas` entry of its own increments
  *another* model's bucket instead of going unmetered. Give every backend in
  `targetRefs` its own entry.
- **Weights are not failover.** A 90/10 split with the primary scaled to zero
  returns 503 for 90% of requests; retries do not help, because an empty cluster
  is "no healthy upstream" and matches no retry trigger. Real failover needs
  `healthCheck` or `outlierDetection`, neither of which this blueprint
  configures. (`semantic-router-timeouts-retries-failover-test-plan.md`)
- **Version skew is unmeasured.** Envoy Gateway v1.8.1 paired with a
  `main`-based AI Gateway controller is a combination nobody has run in
  production here. Watch the `envoy-gateway` logs for extension-manager
  translation errors after switching images.

## Differences from the `semantic-router` blueprint

| | `semantic-router` | this blueprint |
|---|---|---|
| Delivery | ArgoCD Application from a Gitea overlay | `helm upgrade --install` |
| Envoy Gateway / AI Gateway | already installed by cluster-forge | installed here |
| Edge | shared `https` Gateway, TLS terminated, public hostname | ClusterIP + port-forward, no TLS |
| Dashboard | `HTTPRoute` on the shared Gateway | port-forward |
| AI Gateway image | pinned by cluster-forge core | overridable per install |
| Rate limit service | opt-in via `enabledApps` | always installed |
